# Эксплуатация: наблюдение и разбор сбоев

Документ отвечает на один вопрос: «что-то сломалось — куда смотреть».
Установка сервера описана в [`deployment.md`](deployment.md).

Все команды выполняются на сервере из каталога репозитория.

---

## 1. Что у нас есть для наблюдения

Своего мониторинга проект не разворачивает — это было бы отдельной
системой со своей эксплуатацией. Вместо этого:

| Источник                | Как смотреть                       | Что показывает                           |
| ----------------------- | ---------------------------------- | ---------------------------------------- |
| Логи приложения         | `make prod-logs s=backend`         | каждый HTTP-запрос, ошибки               |
| Логи воркера            | `make prod-logs s=worker`          | доставка уведомлений, обработка картинок |
| Логи прокси             | `make prod-logs s=proxy`           | TLS, маршрутизация, коды ответов         |
| Liveness                | `curl https://oinau-pro.kz/health` | процесс отвечает                         |
| Readiness               | `make prod-health`                 | состояние PostgreSQL, Redis, R2          |
| Состояние контейнеров   | `make prod-ps`                     | healthy / unhealthy / restarting         |
| Sentry (если задан DSN) | sentry.io                          | необработанные исключения                |

### Формат логов

В production логи — построчный JSON (`LOG_FORMAT=json`). Каждая запись
несёт `request_id`, поэтому весь путь одного запроса собирается фильтром:

```bash
make prod-logs s=backend | grep '"request_id":"7f3c…"'
```

Тот же идентификатор возвращается клиенту в заголовке `X-Request-ID` и
попадает в тело ошибки. Если пользователь прислал скриншот с ошибкой —
в нём есть `request_id`, и по нему находится вся история запроса.

Записи `http_request` содержат метод, путь, код ответа и длительность.
Строка запроса (query) в лог не пишется, тело запроса — тоже.

### Чего в логах нет и быть не должно

Пароли, JWT, refresh-токены, ключи API, токен Telegram-бота, пароль SMTP,
ключи R2, реквизиты 1С. Отдельно стоит помнить, почему это не само собой:
токен Telegram-бота стоит **в пути URL** Bot API, и логгер `httpx`,
печатающий строку запроса на уровне INFO, раздавал бы ключ от рассылки
всем, кто читает журнал. Приложение приглушает `httpx`/`httpcore` до
WARNING (`app/core/logging.py`), в том числе на импорте — воркер может не
вызвать `configure_logging()`. Это закреплено тестом; не снимайте.

IP-адреса в аудите хранятся хешем (`ip_hash`) и наружу не отдаются.

### Внешняя проверка доступности

Настройте любой аптайм-монитор (UptimeRobot, Better Stack, проверка
Cloudflare) на `https://oinau-pro.kz/health` с интервалом 1–5 минут.
Эндпоинт не ходит в зависимости и отвечает быстро.

`/health/ready` наружу закрыт (прокси отдаёт 404): он перечисляет, какая
именно зависимость сломана, и это диагностика для нас, а не для
посторонних.

## 2. Разбор сбоев

### Сайт не открывается

```bash
make prod-ps                 # что не healthy
make prod-logs s=proxy       # TLS, маршруты
curl -sI https://oinau-pro.kz
```

Типичные причины по порядку вероятности:

1. **Контейнер `web` или `proxy` перезапускается.** Смотрите его логи;
   чаще всего кончилась память (`dmesg | grep -i oom`).
2. **Сертификат не выпущен.** В логах прокси — ошибки ACME. Проверьте,
   что Cloudflare в режиме `Full (strict)` (при `Flexible` получается
   цикл редиректов) и что порт 80 открыт.
3. **Проблема на стороне Cloudflare.** Ошибка 5xx со страницей
   Cloudflare, а не нашей, означает, что до сервера запрос не дошёл.
   Временно переключите DNS-запись в «DNS only» и проверьте напрямую.

### Ошибка 502/503 на всём сайте

`backend` не отвечает. Смотрите `make prod-logs s=backend`.

- Backend не стартует и пишет ошибку конфигурации — значит,
  `.env.production` заполнен неверно. Сообщение называет конкретные поля.
  Это штатное поведение: запуск с dev-настройками запрещён намеренно.
- Backend стартует, но падает на запросах — смотрите трассировку по
  `request_id`.

### База недоступна

```bash
make prod-health             # покажет postgres: error
make prod-logs s=postgres
```

- `FATAL: password authentication failed` — `POSTGRES_PASSWORD` в
  `.env.production` разошёлся с паролем внутри тома. Пароль задаётся
  **только при первичной инициализации тома**; смена переменной задним
  числом пароль в базе не меняет. Меняйте через
  `ALTER USER … WITH PASSWORD …`, затем правьте переменную.
- `No space left on device` — кончился диск. Первым делом
  `docker system prune -f` и проверка `/var/backups/oinau`.
- `too many connections` — `DB_POOL_SIZE` × `UVICORN_WORKERS` превысил
  `max_connections`. Уменьшите пул или число процессов.

Пока база недоступна, сайт не работает: каталог читается из неё.

### Redis недоступен

```bash
make prod-health             # redis: error
make prod-logs s=redis
```

Что при этом продолжает работать, а что нет:

| Функция                    | Поведение без Redis                                                     |
| -------------------------- | ----------------------------------------------------------------------- |
| Создание заявки            | **работает**; событие лежит в `notification_outbox`                     |
| Ограничение частоты        | пропускает запросы (fail-open) + запись `rate_limit_unavailable` в логе |
| Отправка уведомлений       | откладывается до появления Redis                                        |
| Обработка изображений      | откладывается; картинка остаётся в статусе PROCESSING                   |
| Предпросмотр Excel-импорта | недоступен                                                              |

Решение «fail-open» для ограничения частоты сознательное: обратное
означало бы, что падение кеша роняет вход в админку и приём заявок.
После восстановления Redis минутный проход `sweep_notifications`
подберёт всё накопившееся сам — вмешательство не требуется.

### Воркер остановился

```bash
make prod-ps                 # worker: unhealthy
make prod-logs s=worker
```

Здоровье воркера определяется ключом в Redis, который он обновляет
каждые 30 секунд; зависший процесс перестаёт его обновлять и признаётся
нездоровым. Перезапуск:

```bash
docker compose -f infra/docker/compose.prod.yaml --env-file .env.production restart worker
```

Накопившееся не теряется: события остаются в `notification_outbox`,
а строка, застрявшая в статусе `sending`, снова становится доступной
через 10 минут.

Очередь уведомлений:

```sql
SELECT status, count(*) FROM notification_outbox GROUP BY status;
```

`failed` означает, что исчерпаны все попытки (`NOTIFY_MAX_ATTEMPTS`).
Такие события сами не повторяются — разбирайтесь с причиной по
`last_error`.

### Telegram не доставляет

Смотрите `last_error` в `notification_outbox` для канала `telegram`.

- `skipped` — канал не настроен (`TELEGRAM_BOT_TOKEN` или
  `TELEGRAM_CHAT_ID` пусты). Это не ошибка, а выключенный канал.
- `chat not found` — бот не добавлен в чат либо неверный `chat_id`.
- `message thread not found` — неверный `TELEGRAM_MESSAGE_THREAD_ID`,
  тему удалили, либо тема задана для чата, который не является
  супергруппой с темами. Повторов не будет: это ошибка конфигурации,
  а не сбой. Исправьте переменную и перезапустите **воркер** — именно
  он отправляет (`make prod-up` перезапустит и его, и backend).
- `403` при заданной теме — у бота есть право писать в группу, но не
  в эту тему. Выдаётся в настройках темы, а не группы.
- `bot was blocked by the user` — для личных чатов: пользователь
  заблокировал бота.
- Таймауты — проверьте исходящий доступ с сервера к `api.telegram.org`.

Записи со статусом `failed` сами не повторяются. После исправления
переменных заявку нужно оставить заново — или, если сообщение важно,
вернуть конкретную запись в очередь вручную:
`UPDATE notification_outbox SET status='pending', attempts=0,
available_at=now() WHERE id = …;`

Токен в логах не появится ни при какой ошибке — он вырезан вместе со
строкой запроса `httpx`.

### Почта не уходит

- `skipped` для `email` — не заполнен `NOTIFY_EMAILS` (деловые письма)
  либо выключены уведомления целиком (`NOTIFICATIONS_ENABLED=false`).
- Ошибки аутентификации — `SMTP_USER`/`SMTP_PASSWORD`.
- Таймаут — проверьте, не закрыт ли исходящий 587/465 у хостера
  (некоторые провайдеры блокируют SMTP наружу по умолчанию).
- Письма уходят, но не доходят — почти всегда SPF/DKIM/DMARC у домена
  `oinau-pro.kz`. Проверяется на стороне почтового сервиса, не здесь.

Письма клиентам (подтверждение адреса, сброс пароля) и деловые письма о
заявках — разные каналы: первые уходят всегда, вторые только при
заполненном `NOTIFY_EMAILS`.

### R2 недоступен или картинки не показываются

```bash
make prod-health             # storage: error
```

- `storage: error` — неверные ключи R2, неверный `S3_ENDPOINT_URL` или
  удалённый бакет.
- Готовность есть, но картинок нет в браузере — проверьте
  `CDN_BASE_URL`, `NEXT_PUBLIC_CDN_BASE_URL` и публичный домен бакета.
  Если они разошлись, Next.js откажется отдавать изображение с чужого
  хоста (ошибка в консоли про `remotePatterns`), а исправление требует
  **пересборки** образа витрины.
- Загрузка из админки падает на шаге PUT — на бакете нет CORS-политики
  (см. `deployment.md`, раздел 3).
- Картинка «залипла» в PROCESSING — не работает воркер, см. выше.

### Обмен с 1С отвечает 503

Ожидаемо при `ONE_C_INTEGRATION_ENABLED=false`. Проверка выключателя
идёт **до** аутентификации, поэтому 503 получают все, включая верный
ключ. Это защита от случайно включённого боевого обмена.

При включённом обмене 403 означает либо неверный ключ (`X-API-Key`),
либо адрес вне `INTEGRATION_IP_ALLOWLIST`.

### Заявки перестали приходить с сайта

Проверьте по порядку:

1. `notification_outbox` — события создаются? Если да, проблема в
   доставке, а не в приёме.
2. Ограничение частоты: `RATE_LIMIT_PUBLIC_FORM` — 5 заявок в час с
   одного адреса. Если `TRUSTED_PROXY_HOPS` задан неверно, все посетители
   выглядят одним клиентом, и шестой за час получает отказ. Это самая
   частая причина «форма не работает» после переезда.

## 3. Регулярные проверки

| Когда                     | Что                                                                     |
| ------------------------- | ----------------------------------------------------------------------- |
| Ежедневно (автоматически) | резервная копия: `systemctl status oinau-backup.timer`                  |
| Еженедельно               | `make prod-ps`, свободное место (`df -h`), `journalctl -u oinau-backup` |
| Ежемесячно                | восстановление копии: `make prod-restore-verify f=…`                    |
| Ежемесячно                | `apt list --upgradable`, обновление образов и пересборка                |
| При каждом обновлении     | копия **до** миграций, `make prod-health` после                         |

## 4. Чего делать нельзя

- Открывать порты PostgreSQL, Redis или backend наружу «на время
  отладки». Для доступа к базе есть `docker compose exec` и SSH-туннель.
- Запускать `alembic downgrade` в production. Откат — только
  восстановлением из копии.
- Запускать `app.scripts.seed` на боевой базе. Скрипт сам откажется, но
  не полагайтесь на это.
- Снимать приглушение `httpx` в логировании.
- Хранить резервные копии только на том же диске, где база.
