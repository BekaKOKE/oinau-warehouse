# ADR-0006. Короткий JWT + непрозрачный refresh с ротацией

**Статус:** Принято
**Дата:** 2026-09-09

## Контекст

Нужен механизм сессий для админки, которая живёт на отдельном поддомене
и общается с API из браузера.

## Решение

- **Access-токен** — JWT HS256, 15 минут, передаётся в заголовке
  `Authorization`, хранится в памяти приложения.
- **Refresh-токен** — непрозрачная случайная строка (48 байт), хранится
  в httpOnly cookie, в БД лежит только SHA-256 от неё.
- **Ротация**: каждое обновление выдаёт новую пару и отзывает старый
  refresh. Повторное предъявление отозванного токена отзывает всю
  цепочку (`family_id`).
- Пользователь загружается из БД на каждом запросе.

## Обоснование

**Почему refresh не JWT.** Самодостаточный JWT нельзя отозвать без
списка отзыва, то есть без обращения к БД — ровно того, чего JWT должен
был избежать. Непрозрачный токен честнее: одно обращение к
индексированной таблице и полный контроль над отзывом.

**Почему access в памяти, а не в localStorage.** `localStorage` читается
любым JS, поэтому XSS в админке означал бы кражу токена. Память
приложения переживает только текущую вкладку — при перезагрузке
страницы токен восстанавливается через refresh-cookie.

**Почему refresh в cookie, а не в теле ответа.** httpOnly-cookie
недоступна JS, значит XSS не даёт долгоживущего доступа. CSRF при этом
не возникает: cookie имеет `SameSite=strict` и путь, ограниченный
эндпоинтами аутентификации, а все прикладные запросы авторизуются
заголовком, который браузер сам не подставляет.

**Почему `SameSite=strict` работает.** `admin.oinau-pro.kz` и
`api.oinau-pro.kz` — один сайт (общий eTLD+1). Если API когда-нибудь
вынесут на другой домен, значение придётся менять на `none` вместе
с обязательным `Secure`, и это надо помнить.

**Почему пользователь читается из БД на каждом запросе.** Это один
индексный запрос. Взамен отключение сотрудника, смена роли и мягкое
удаление действуют немедленно, а не через 15 минут. Для админки
с десятками запросов в минуту цена нулевая.

**Почему прав нет внутри токена.** Иначе изменение состава прав роли
не подействовало бы на уже выданные токены, и понижение доступа
откладывалось бы до их истечения.

## Последствия

- Обнаружение переиспользования токена отзывает и легитимную сессию:
  пользователь входит заново. Это осознанная цена за то, что украденный
  токен перестаёт работать сразу.
- Требуется хранить `refresh_tokens` и периодически чистить истёкшие
  записи (фоновая задача, этап 8).
