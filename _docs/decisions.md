## 2026-10-13 — Architecture for the warehouse feature

**Context.** The plan adds a stock check, packing documents (1 summary + N packages with QR codes) and a two-way exchange with 1С to the existing FastAPI + Next.js monorepo. Before choosing, we read the code and found four facts that shaped the choices:

1. `stocks.synced_at` is **not** updated when a 1С push sends the same number (`StockSyncService._apply_stock` in `app/modules/integration/service_sync.py`). So it can't be used for plan rule D25 ("subtract until a newer stock update arrives").
2. Request statuses can move freely (`AdminRequestService.update_status`), and the admin API has no way to edit request items. So "locking items" (D17) really means guarding status changes.
3. The admin request API returns prices and client contacts. A warehouse user can't just get `request.read`.
4. 1С can already send `reserved` through `inventory/bulk-upsert`.

The architecture rule stays in force: **the site never changes stock** (`app/modules/inventory/models.py` — no `stock_movements`). Nothing below writes to `stocks.quantity` or `stocks.reserved`.

### T1. Data model: summary → lines → packages

- **Decision.** Three new tables: `warehouse_documents` (the summary, the only write-off document), `warehouse_document_lines` (one row per request line, with snapshots and "available at check"), and `warehouse_packages` (each linked to one line, with a quantity and a random token).
- **Options compared.**
  - A. Summary → lines → packages *(chosen)*.
  - B. Summary + packages only, with lines computed by grouping.
  - C. One generic `documents` table with a type column.
- **Why.**
  - The summary has real, stored lines, so the document 1С writes off from is a fixed record, not something computed.
  - "Available at check" has a natural home on the line.
  - Rule D8 ("only the summary writes off") follows from the shape of the schema instead of being a convention.
  - Mixed boxes later only need one extra table.
- **Cost.** Three tables instead of two.

### T2. 1С status is stored as timestamps, not a status column

- **Decision.** `exported_at`, `write_off_confirmed_at` and `cancel_exported_at` on `warehouse_documents`. The 1С status shown in the UI is computed from them.
- **Why.**
  - The same pattern as `requests.exported_at` + `/ack`.
  - It gives the exact times that rule D25 and audit need.
  - The warehouse status and 1С status stay separate (plan D20).

### T3. At most one active document per request, enforced by the database

- **Decision.** A partial unique index on `warehouse_documents(request_id) WHERE status IN ('CREATED','PACKED')`.
- **Why.**
  - Checking in the code first doesn't protect against a race.
  - The database is the last guarantee. This is the same idea as `app/core/integrity.py`, which turns index violations into a clear 409.

### T4. Code location

- **Decision.**
  - A new backend module `app/modules/warehouse/`.
  - The 1С part in `app/modules/integration/service_warehouse.py`, with thin routes in `app/api/v1/integration.py`.
  - A new `packing` section in `apps/admin`.
  - The public QR page at `apps/web` → `/check/[token]`.
- **Options compared.**
  - A. New module *(chosen)*.
  - B. Inside `modules/requests/`.
  - C. Inside `modules/inventory/`.
- **Why.**
  - `requests` is the sales domain and `inventory` only holds current stock; documents fit neither.
  - Following the existing 1С layout (`service_requests.py`, `service_sync.py`) keeps the integration API in one place.
  - The QR page must work without login, so it can't live in the admin app.
  - Rendering HTML in the backend would break the backend/web split (`docs/architecture.md`, section 3).

### T5. Printing and QR: HTML page printed from the browser, QR as SVG drawn in the browser

- **Decision.** A print-only admin page with A4 print CSS (one page for the summary, one page per package). The QR code is drawn as SVG in the browser by a small npm library and holds only the URL `PUBLIC_SITE_URL/check/<token>`.
- **Options compared.**
  - A. Browser print *(chosen)*.
  - B. Backend PDF (WeasyPrint/ReportLab).
  - C. PDF generated by the worker and stored in object storage.
- **Why.**
  - Matches plan D28 (A4 from the browser).
  - Adds no system libraries or Cyrillic fonts to the backend image.
  - Keeps to the rule that the backend doesn't serve binary files.
- **Cost.**
  - Small differences between browsers.
  - No stored copy of what was printed.
  - To revisit when the label printer is added (then QR generation should move to the backend).

### T6. 1С API: copy the requests pattern

- **Decision.** `GET /integration/warehouse-documents` (pending items) and, per document, `POST …/{uuid}/ack`, `POST …/{uuid}/write-off`, `POST …/{uuid}/cancel-ack`. New scopes `warehouse:read` and `warehouse:write`.
- **Options compared.**
  - A. Requests pattern *(chosen)*.
  - B. An event feed with a cursor.
  - C. Adding documents to `GET /integration/requests`.
- **Why.**
  - The 1С developer already knows this pattern, and it's easy to test.
  - Option B is a new pattern in the project.
  - Option C doesn't work, because requests are confirmed once, at intake, before any documents exist.

### T7. Closing the D25 gap: a per-row "last seen in a 1С push" time

- **Decision.** A new column `stocks.reported_at`. The 1С stock upsert sets it for **every** row in the push, even when the numbers didn't change. A confirmed write-off stops being subtracted only when `reported_at > write_off_confirmed_at`.
- **Options compared.**
  - (i) Per-row `reported_at` *(chosen)*.
  - (ii) The time of the last successful full push from `sync_log`.
  - (iii) The write-off confirmation carries the new stock numbers.
- **Why.**
  - It works whatever format 1С ends up using.
  - (ii) only works if 1С always sends full snapshots.
  - (iii) depends on a 1С format we don't know yet.
- **Cost.** A small change to `StockSyncService._apply_stock`. `synced_at` keeps its meaning ("when the data really changed").

### T8. Warehouse role

- **Decision.**
  - A new `UserRole.WAREHOUSE` and new permissions `warehouse.read`, `warehouse.pack` and `warehouse.cancel`, also given to MANAGER, ADMIN and SUPERADMIN.
  - Separate `/admin/warehouse/*` endpoints whose response schemas have no price or contact fields.
- **Options compared.**
  - A. New role + permissions *(chosen)*.
  - B. Reuse existing roles and hide fields per permission.
  - C. Per-user permission settings.
- **Why.**
  - Matches the architecture rule "check permissions, not roles" (`app/modules/users/permissions.py`).
  - Data can't leak because the fields don't exist in the schemas (the same approach as the integration status endpoint).
  - Option C was rejected earlier in `docs/architecture.md` §12.
- **Cost.** A migration, because `users.role` has a check constraint listing the allowed roles.

### T9. Same-time packing

- **Decision.** Inside one transaction:
  1. A global transaction-level advisory lock for all packing (`pg_advisory_xact_lock`).
  2. A row lock on the request (`AdminRequestRepository.get_for_update`).
  3. An idempotency key on the "create split" call.
  4. The unique index from T3 as the final guard.
- **Options compared.**
  - A. Locking product rows in sorted order.
  - B. One global lock *(chosen)*.
  - C. SERIALIZABLE transactions with retry.
  - D. A "committed quantity" counter on `stocks` with a check constraint.
- **Why.**
  - Simplest to get right, with no deadlocks.
  - The same technique the Excel import already uses (`CATALOG_IMPORT_LOCK_KEY`).
  - At tens of packings a day, waiting costs milliseconds.
  - Option D is reservation in disguise and would make 1С pushes fail.
- **Revisit when** packing volume grows enough for the lock to cause waiting → move to option A.

### T10. Available stock includes `reserved`

- **Decision.** `available = quantity − reserved − (site documents not yet covered by a 1С stock update)`.
- **Why.**
  - `reserved` comes from 1С, and 1С is the source of truth.
  - The public availability formula in `docs/architecture.md` §6.5 also subtracts `reserved`.
- **Risk.** If 1С's `reserved` already includes this same request, the request is subtracted twice. The result is too low ("short" when it isn't), which is safe but annoying. → Open question Q1.

## Open questions (for the 1С developer and the business)

| # | Question | Who | What depends on it |
|---|---|---|---|
| Q1 | Does 1С's `reserved` already include goods reserved for the same website request? | 1С developer | T10. If yes, the request is subtracted twice; we would need to exclude the request's own reservation, or ignore `reserved` for linked requests. |
| Q2 | Does every stock push include **every** product, or only changed ones? | 1С developer | T7. If only changed ones, `reported_at` won't move for products 1С didn't send, so a confirmed document stays subtracted until that product changes in 1С. That's safe but too low. Fix: 1С sends full snapshots, or the confirmation includes the affected products' new stock. |
| Q3 | Does 1С need to confirm the **reversal** of a write-off (like it confirms the write-off)? | 1С developer | Whether a 4th timestamp/endpoint is needed. |
| Q4 | Who may cancel documents: the warehouse person, the manager, or both? Is a reason required? | Business | `warehouse.cancel` assignment. The design assumes both, with a required reason. |
| Q5 | Language of printed documents and the QR page (RU / KZ / both)? | Business | Print and web templates. The design assumes Russian. |
