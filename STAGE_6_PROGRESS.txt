1. ЧТО РЕАЛИЗОВАНО
--------------------------------------------------------------------------------

Публичный сайт OINAU PRO на существующем стеке проекта (Next.js 15 App Router,
React 19, TypeScript strict, pnpm-воркспейс). Личный кабинет, админ-интерфейс
и интеграции (Telegram / Email / WhatsApp API / 1С) НЕ реализованы — это
следующие этапы.

Дизайн перенесён из «Дизайн сайта комплектующих.zip» (OINAU PRO.dc.html):
визуальный язык, композиция, палитра (#0e1620 / #0b5fd0 / #2b8bff / #7fb4ff
на светлом тёплом сером), Manrope + IBM Plex Mono, скруглённые карточки,
hero с фотографией площадки и светящимися hotspot-плашками. HTML макета
НЕ переносился: всё переписано обычными React-компонентами с CSS-модулями.

Ключевые блоки:
  * Hero с изображением площадки и 10 интерактивными hotspot-точками.
    Точка — настоящая ссылка в раздел каталога с числом позиций из API.
    Координаты и привязка к разделу вынесены в конфигурационный слой
    (apps/web/src/lib/hotspots.ts): backend не хранит «узлы площадки»
    как сущность, и когда она появится, изменится только эта функция.
    Если категории нет в каталоге, точка ведёт в каталог с поиском,
    а не в битую ссылку.
  * Секция «Категории комплектующих» — из GET /public/categories,
    без хардкода каталога.
  * Каталог: поиск, фильтр наличия, диапазон цены, сортировка,
    постраничная навигация, вкладки разделов, снимаемые плашки фильтров.
  * Карточка товара: галерея с миниатюрами, цена по типу, таблица ступеней,
    характеристики, минимальная партия, хлебные крошки, похожие позиции.
  * Заявка: панель с составом, изменение количества, контактная форма,
    отправка, номер заявки. Оплаты и checkout нет.
  * Избранное (хранится в браузере), плавающая кнопка WhatsApp,
    страницы контактов, доставки и FAQ из CMS.

3. ПОДКЛЮЧЁННЫЕ API
--------------------------------------------------------------------------------

  GET  /api/v1/public/categories               дерево категорий
  GET  /api/v1/public/categories/{slug}        страница раздела
  GET  /api/v1/public/products                 список с фильтрами
  GET  /api/v1/public/products/{slug}          карточка
  GET  /api/v1/public/products/{slug}/related  похожие
  GET  /api/v1/public/content/home             главная
  GET  /api/v1/public/content/contacts         контакты + реквизиты
  GET  /api/v1/public/content/delivery         доставка
  GET  /api/v1/public/content/faq              вопросы
  GET  /api/v1/public/content/settings         шапка и подвал
  GET  /api/v1/public/regions                  регионы для формы заявки (НОВЫЙ)
  POST /api/v1/public/requests                 отправка заявки

Типизированный клиент: apps/web/src/lib/api/{client,catalog,content,requests}.ts.
Хаотичных fetch() по компонентам нет. Обрабатываются loading / empty / error /
retry / обрыв сети. Ошибки backend показываются по коду: product_unavailable
называет артикулы, quantity_below_minimum — минимальные партии,
rate_limited — понятное объяснение.

Decimal-значения приходят строками и строками остаются: витрина их
не приводит к number для арифметики. Все четыре типа цены разведены:
FIXED «X ₸ / шт», FROM и TIERED «от X ₸», ON_REQUEST «Цена по запросу».
Цена никогда не выдумывается: если суммы нет, показывается запрос, а не ноль.

4. ИЗМЕНЕНИЯ В BACKEND (минимальные, архитектура не менялась)
--------------------------------------------------------------------------------

Функциональные:
  * GET /api/v1/public/regions — новый эндпоинт.
    Без него форма заявки не могла бы заполнить обязательный region_id:
    публичного справочника регионов не было.
    Файлы: app/modules/geo/{schemas,repository,router_public}.py.
  * CategoryNode.product_count и CategoryDetail.product_count — новые поля.
    Дизайн требует счётчик позиций на карточке раздела и на hotspot;
    посчитать его на клиенте нечем — список грузится постранично.
    Считается вся ветка (COUNT DISTINCT по подкатегориям), то есть ровно
    столько, сколько покажет страница раздела.
    Файлы: catalog/{schemas,repository,service}.py. Миграция не нужна —
    это поля ответа, а не колонки (alembic check чист).

Исправления, без которых локальный запуск невозможен:
  * app/core/config.py — списочные настройки помечены NoDecode.
    pydantic-settings 2.15 разбирал CORS_ORIGINS=a,b как JSON и падал
    на первой запятой ДО наших валидаторов: запуск с готовым .env.example
    был невозможен.
  * app/core/logging.py — убран structlog.stdlib.add_logger_name.
    В structlog 26 он читает logger.name, которого у PrintLogger нет,
    и приложение падало при старте. Имя модуля теперь привязывает
    get_logger().
  * alembic.ini переведён в ASCII. Alembic читает файл кодировкой системной
    локали, и кириллица в комментариях ломала `alembic upgrade` на Windows
    (cp1251/cp1252). Пояснения перенесены в alembic/env.py.
  * apps/{web,admin}/next.config.ts — output:'standalone' включается только
    переменной NEXT_BUILD_STANDALONE=1, которую задаёт Dockerfile.
    Standalone раскладывает зависимости символическими ссылками, и локальная
    сборка на Windows падала с EPERM уже ПОСЛЕ успешной сборки страниц.
  * Makefile: цель gen-types писала файл в packages/api-types/packages/...
    (относительный путь резолвился от каталога пакета).
  * packages/{api-types,api-client} и apps/{web,admin}: добавлена зависимость
    @oinau/config — её tsconfig расширяют, но в зависимостях не объявляли,
    из-за чего pnpm не линковал пакет и tsc не находил базовый конфиг.
  * .env.example: у INTEGRATION_IP_ALLOWLIST и NOTIFY_EMAILS комментарий
    стоял в одной строке с ПУСТЫМ значением. python-dotenv очищает хвостовой
    комментарий только у непустого значения, поэтому на чистой установке
    INTEGRATION_IP_ALLOWLIST получал непустое мусорное значение и включал
    проверку IP, блокируя интеграционный API. Комментарии вынесены
    на отдельные строки, поведение закреплено тестами.

Отдельная правка hero по итогам визуальной проверки — шесть дефектов:

  1. Точки не нажимались. Текстовый блок (`.content`, z-index 2) был
     отдельным слоем во всю ширину поверх фотографии и перехватывал все
     клики. Текст и снимок разведены в две колонки сетки: кликабельно
     ровно то, что видно, ловушек со слоями больше нет.
  2. Плашки выглядели блёклыми: затемнения кадра (z-index 7) рисовались
     ПОВЕРХ них (z-index 3). Слой точек поднят над затемнениями.
  3. Снимок показывался не целиком: кадр 3:2 был прижат вправо внутри
     блока с `overflow: hidden`, и левая часть срезалась. Кадр переведён
     в поток, виден полностью, пропорция совпадает со снимком — проценты
     из lib/hotspots.ts ложатся на фотографию точно при любой ширине.
  4. Плашки были мелкими и наезжали друг на друга. Размеры получили
     минимумы (высота цели не меньше 44 px), подпись и счётчик разведены
     в две строки, на узком экране плашки заменяются точками-ориентирами
     и прокручиваемым рядом ссылок с полноразмерными целями.
  5. Три точки подписывались одинаково — «Пластиковые детали», ещё две —
     «Крепления и подвесы»: подпись бралась из названия раздела, а узлов
     на один раздел приходится несколько. Теперь подпись — название узла
     («Крыша», «Горка», «Стенка для лазания»), а раздел назначения
     и число позиций уходят в доступное имя ссылки.

  6. Ссылка на снимок вела на удалённый файл hero-playground.webp.
     Подключён переданный чистый снимок playground.webp.

Края снимка растворяются в тёмном фоне градиентами по всем четырём
сторонам плюс радиальным гашением углов — прямоугольник с резкой
границей выглядел наклейкой. Сам кадр увеличен: текст выровнен по общей
сетке сайта, а фотография уходит почти к правому краю экрана (до 1060 px
против прежних ~800). Точек стало 11 — добавлены «Качели»: левая треть
снимка пустовала, а раздел «Сиденья качелей» не был представлен вовсе.

Координаты в lib/hotspots.ts промерены заново по новому снимку:
композиция другая, и прежние значения указывали мимо объектов.
Раскладка закреплена тестами: ни одна плашка не выходит за кадр
и не пересекается с соседней.

Отдельно исправлено при проверке: заголовок страницы получал бренд дважды
(«Канат Ø16 мм — OINAU PRO — OINAU PRO»), потому что buildMetadata дописывал

а бренд не приписывается, если он уже есть в тексте из CMS. Закреплено
в tests/seo.test.ts.

E2E: браузерный стек (Playwright/Cypress) в проекте отсутствовал; установка
браузеров признана чрезмерной для этого этапа. Вместо него:

  * сценарий заявки дополнительно проверен на живом API (см. раздел 9);
