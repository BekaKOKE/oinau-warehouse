2. ЧТО РЕАЛИЗОВАНО
------------------

2.1. Очередь исходящих событий (outbox)
  Почему таблица, а не «поставить задачу после коммита»: падение
  процесса между коммитом заявки и постановкой задачи теряет событие
  молча. Событие пишется строкой в notification_outbox ТОЙ ЖЕ
  транзакцией, что и заявка. Redis остаётся ускорителем: он будит
  воркер сразу, а раз в минуту cron-проход подбирает всё, что Redis
  потерял, и всё, что ждёт повтора.

  Исходы провайдера: sent / skipped (канал выключен) / retry
  (таймаут, сеть, 5xx, 429) / failed (4xx, неверный адрес).
  Повтор — экспоненциальный откат, потолок 6 часов, после
  NOTIFY_MAX_ATTEMPTS запись становится failed.
  Захват записи — один UPDATE ... RETURNING с SKIP LOCKED: два воркера
  не отправят одно письмо дважды. Зависшая в sending запись
  возвращается в работу через 10 минут сама.

  Дубли невозможны физически: уникальный частичный индекс по
  dedup_key. У писем аутентификации ключа намеренно НЕТ — «отправить
  ссылку ещё раз» обязано работать.

2.2. Провайдеры
  app/infrastructure/notifications/: base.py (протокол
  NotificationProvider, DeliveryResult), telegram.py, email.py,
  registry.py. Добавление WhatsApp не требует изменений в доменах.

  Telegram — httpx, таймаут, коды 408/429/5xx → повтор, 4xx → отказ.
  Email — стандартный smtplib в отдельном потоке (asyncio.to_thread).
  Асинхронная библиотека не добавлялась: письма шлёт воркер, где
  блокировка потока никого не задерживает, а новая зависимость в
  проекте, уже хранящем SMTP-пароль, — лишняя поверхность обновлений.
  Письмо всегда multipart: текст + HTML.

2.3. События
  request.created            → Telegram (все чаты) + деловая почта
  request.status_changed     → письмо клиенту, если адрес подтверждён
  request.comment_added      → письмо клиенту, только видимый комментарий
  customer.email_verification → письмо клиенту
  customer.password_reset     → письмо клиенту

  Внутренний комментарий не уходит клиенту никуда. Текст ВИДИМОГО
  комментария в письмо тоже не копируется — только ссылка в кабинет.
  На неподтверждённый адрес письма не отправляются.

2.4. Письма кабинета (этап 7 → этап 9)
  Интерфейс AccountMailer сохранён без изменений; появилась реализация
  OutboxAccountMailer, которая кладёт письмо в очередь. Второй системы
  аутентификации не создано: токены по-прежнему выпускает
  CustomerAuthService, ссылки собираются там же, где и раньше.

2.5. Обмен с 1С
  Эндпоинты по architecture.md, 7.3:
    GET  /integration/health
    POST /integration/catalog/products/bulk-upsert   (catalog:write)
    POST /integration/pricing/bulk-upsert            (pricing:write)
    POST /integration/inventory/bulk-upsert          (inventory:write)
    GET  /integration/requests                       (requests:read)
    POST /integration/requests/{uuid}/ack            (requests:read)

  Сопоставление: external_id, при его отсутствии sku. По названию —
  никогда. При первом сопоставлении по артикулу GUID запоминается.

  Обмен НЕ создаёт товары (нет slug, описания, картинок — витрина
  показала бы пустую карточку), НЕ создаёт склады, НЕ удаляет ничего
  по отсутствию в пакете, НЕ трогает описания, SEO, изображения и
  название товара.

  Частичный успех: битая строка откатывается через SAVEPOINT, пакет
  применяется. Отчёт построчный: created/updated/skipped/failed + код
  и пояснение.

  Идемпотентность двойная: upsert по стабильному ключу идемпотентен
  сам по себе, плюс полностью одинаковый пакет узнаётся по SHA-256
  в течение 6 часов и отдаёт прежний итог (duplicate=true). Частично
  применённый пакет дублем НЕ считается — отбракованные строки должны
  получить второй шанс.

  Цены: набор ступеней заменяется целиком; пересекающиеся ступени
  отбраковываются ДО записи, иначе пакет упал бы на EXCLUDE базы.
  Остатки: available = quantity - reserved вычисляется, не хранится;
  резерв больше остатка отбраковывается. Публичное наличие — только
  по активным складам, точные количества наружу не отдаются.

  Заявки: 1С забирает невыгруженные и подтверждает приём. Повторный
  ack возвращает прежние external_id и exported_at, а не переписывает.

2.6. Аутентификация интеграции
  Таблица api_keys: в базе только SHA-256, ключ показывается один раз.
  Заголовок X-API-Key (не Authorization: Bearer — там JWT сотрудника).
  Scope по сущностям: обмен остатками не может переписать каталог.
  Порядок проверок: выключатель (503) → IP (401) → ключ (401) →
  scope (403). Ответы «ключ неизвестен» и «ключ отозван» неотличимы.
  Норма частоты считается НА КЛЮЧ: 1С обычно за общим офисным NAT.
  Размер тела проверяется по Content-Length до разбора JSON.

  Ключ выдаётся скриптом app/scripts/create_api_key.py (make api-key),
  а не кнопкой в админке: это операция уровня развёртывания.

2.7. Журналы
  sync_log — как прошёл обмен (счётчики, длительность, имя ключа,
  SHA-256 пакета). Содержимое пакета не хранится.
  audit_log — изменения объектов ТЕМИ ЖЕ действиями, что и Admin API
  (catalog.product_updated, pricing.updated, inventory.stock_updated),
  но с actor="1c". История товара читается одинаково для любого канала.

2.8. Админка
  GET /api/v1/admin/integration/status (право settings.write) и раздел
  «Интеграции»: состояние каналов, счётчики очереди, число активных
  ключей, последние обмены и последний сбой.
  Реквизитов в схемах ответа НЕТ ни одного поля — показать их случайно
  невозможно. Раздел только читает.


3. НАЙДЕНО И ИСПРАВЛЕНО ПО ХОДУ
-------------------------------

3.1. Утечка токена бота в журнал (нашёл тест)
  httpx на уровне INFO печатает строку запроса целиком, а токен
  Telegram стоит В ПУТИ URL. При LOG_LEVEL=INFO токен попадал бы в
  журнал. Логгеры httpx и httpcore приглушены до WARNING в
  app/core/logging.py; приглушение применяется и при импорте модуля,
  потому что воркер может не звать configure_logging().

3.2. Падение очереди роняло ответ (нашёл тест)
  Побудка воркера после коммита вызывалась без защиты: недоступный
  Redis превращал успешно созданную заявку в 500. Добавлена
  wake_worker() — гасит любое исключение и пишет предупреждение.
  Защита стоит в месте вызова, а не только внутри реализации очереди:
  она не должна зависеть от вежливости конкретного провайдера.

3.3. test_customer_security
  Проверка «клиент не достаёт интеграцию» ожидала 401/404, а получила
  503: выключатель обмена намеренно стоит ПЕРЕД аутентификацией, то
  есть выключенный обмен закрыт для всех. Тест обновлён и усилен —
  дополнительно проверяется, что данных в ответе нет.

---------------------------------------------------
  Внешние системы заменены локальными заглушками (qa_stubs.py):
  HTTP-сервер вместо Bot API и SMTP-сервер вместо почтового. Наружу
  не ушло ничего.

  Уведомления:
   * заявка с витрины → 3 записи в outbox (2 чата + деловая почта),
     все pending; воркер разбужен ровно этими id;

   * регистрация клиента → письмо подтверждения со ссылкой на витрину
     и сроком действия;

9. ОГРАНИЧЕНИЯ ЛОКАЛЬНОГО QA
----------------------------
  Сам процесс arq-воркера против fakeredis не поднимается: заглушка
  рвёт блокирующие соединения (BLPOP). Поэтому доставка запускалась
  тем же кодом, который исполняет задача sweep_notifications
  (NotificationDispatcher.dispatch) — задача воркера является его
  трёхстрочной обёрткой. На настоящем Redis воркер запускается штатно
  (сервис worker в compose.dev.yaml).
